Muse said the GitHub connector didn't exist, then connected anyway

Two connector systems live side by side in Muse: Meta's reviewed directory and the custom connectors your Muse builds on the spot. The "it doesn't exist" message is a catalog miss, not a capability limit, and the workaround is the part worth understanding.

By Marvin Jones

Last checked against the live product: October 5, 2026.

The strangest sentence Muse can say to you is "that connector doesn't exist," delivered seconds before it connects to the thing anyway. That is what happened to reviewer Taylor Arndt, testing Muse after Meta's Connect event: "There was some confusion around GitHub at first. At one point Muse acted like there was not a GitHub connector. But the connector system gave us another path, and eventually I had GitHub connected too. Muse pulled the profile and could work with it."

The irony is that GitHub was, at that very moment, one of the work connectors Meta was explicitly announcing at Connect, alongside Notion, Granola, and Box. The agent denied the existence of something Meta was putting on stage the same week. Once you understand why that happened, the whole connector system makes sense, and so does the warning nobody reads before clicking through.

"Doesn't exist" is the wrong sentence

Muse has two completely different connector systems, and the agent is bad at telling you which one it is talking about.

Directory connectors are the reviewed kind. Meta runs functional, security, and legal review plus end-to-end testing before listing one, and the directory opened September 18 with a sign-in-gated submission form at muse.ai/platform. Alexandr Wang said Meta received more than 1,500 applications in under a week. No review timeline, fees, or revenue-share terms have been published.

Custom connectors are the unreviewed kind. Any Muse user can ask the agent to build a custom connector from a service's API or MCP server, and Meta does not review those; the credentials land in Muse's secure store behind surrogate tokens so the model never holds the raw secret. As one connector template's docs put it: being reachable as a Custom Connector requires nothing from Meta, a user can point Muse at your URL today, and getting listed in the directory is a separate process with review.

So when Muse says a connector doesn't exist, what it usually means is: "I can't find that in my directory list." The second system, the build-it-yourself one, doesn't need the directory at all. That is the "another path" Arndt's Muse found.

What Meta's directory actually contains

There is no single published list from Meta of every connector in the directory, which is part of the problem. The launch set, per Meta's developer materials, included Gmail, Google Calendar, Plaid, Stripe Link, Shopify Catalog, OpenTable, Ticketmaster, and Duffel. Connect 2026 added Walmart, Best Buy, Sephora, Notion, Granola, GitHub, Box, and others. Wang has also listed Gmail, Google Calendar, Outlook, Plaid, OpenTable, Google Docs, Spotify, Function Health, Withings, Tailscale, and Peloton, plus the Meta-native set: Instagram, DMs, Threads, Facebook, Marketplace, Messenger.

Because no SDK or API spec had been published as of the platform's September 18 launch, builders have been documenting the process in the open instead. A third-party tracker, musedirectory.ai, now claims 2,367 live-checked Muse connectors, each health-checked every 15 minutes and labeled Live, Degraded, or Down. Treat the number as the builder's own claim (its press release also positions the site against OpenAI's rival directory), but the Live/Degraded/Down labeling is the first connector-reliability scoreboard anyone has built, and worth bookmarking if you depend on a connector.

Field note

If a service you want is missing from the directory, don't read that as a verdict on the service. The directory is a few weeks old, the review queue is unpublished, and the custom-connector path exists precisely because the directory will always lag behind what the agent can technically reach.

The workaround everyone actually uses

Muse has no connector settings screen for these. The community worked out the flow fast: you paste a setup prompt into a new chat, it names the service's MCP link and asks for OAuth, Muse replies with a sign-in link, you approve it with your account, and Muse saves the connector.

The Postiz guide documents it plainly: "Paste the setup prompt from this page into a new Muse message. It names the Postiz MCP link and asks for OAuth. Muse replies with a sign-in link; approve it with your Postiz account and Muse saves the connector. No API key is needed."

That same paste-a-prompt pattern is now how dozens of small services distribute to Muse users, and community catalogs on GitHub keep the setup prompts organized with capability, authentication, and permission notes per service. It works. It is also, by Meta's own description, the unreviewed lane.

The consent dialog says the quiet part out loud

This is the part worth slowing down for. When you connect a custom connector, Meta's own consent dialog tells you, in plainer language than its help pages, what you are doing. Documented by a builder who read it at connect time:

"Meta doesn't review custom connectors or how they use your information. The agent may take unexpected actions. Grant access with caution and review their privacy policies."

The same dialog asks for openid, profile, email, and offline_access scopes, and offline access means exactly what it says: it keeps working when you are not there, which is the point of the nightly task and also the reason to think about it.

Two technical details soften this, and two don't. Softening: every outbound request passes through Sentinel, the separate authority on your VM that gates connector actions and network egress; and the agent only ever sees surrogate tokens, with real credentials inserted at the network boundary. Not softening: custom connector code runs inside Muse's own runtime cell without the extra privilege separation Meta applies to built-in connectors, and one builder documents that Muse's egress proxy hangs on Server-Sent Events, so connectors must use POST-only streaming, the kind of sharp edge that only shows up when something breaks in production.

Caution

Treat a custom connector like a browser extension: useful, fast to install, and written by whoever wrote it. "Muse doesn't have it" followed by "Muse built it for me in two minutes" is not a safety finding. It is the agent skipping the one review queue Meta built.

What to watch

The connector story is young, and the parts that would change this page are concrete: Meta publishing actual developer documentation (the zero-docs launch is the root of the whole "another path" pattern), a published review timeline for the directory queue, and somebody publishing a per-connector permission-scope matrix, since no canonical "what can this connector read and write" list exists today. I'll update this page when any of that lands. Until then, musedirectory.ai's Live/Degraded/Down tracker is the closest thing to a status page the ecosystem has.

Quick answers

Why does Muse say a connector doesn't exist?

It usually means the connector isn't in Meta's reviewed directory, which opened September 18 and is still being filled. The agent can often build a custom connector to the same service on the spot, which is a separate, unreviewed path.

How do I connect a service that has no directory connector?

Ask Muse to build a custom connector from the service's API or MCP server. Many services publish a setup prompt you paste into a new chat; Muse replies with a sign-in link, you approve it, and the connector is saved. No settings screen is involved.

What's the difference between a directory connector and a custom connector?

Directory connectors go through Meta's functional, security, and legal review and are listed in the built-in directory. Custom connectors are built by the agent for one user from a service's API and are not reviewed by Meta. The consent dialog says so directly.

Is the custom-connector path safe?

It is designed with guardrails: Sentinel gates every outbound request, and the model only sees surrogate tokens, never your raw credentials. But custom connectors skip Meta's review entirely, request scopes like offline access, and run without the privilege separation of built-in connectors. Read the provider's privacy policy and keep the permissions narrow.

Where can I see which connectors are working right now?

The third-party tracker musedirectory.ai claims 2,367 live-checked connectors with health checks every 15 minutes and Live/Degraded/Down labels. Treat it as an independent scoreboard, not a Meta source.

Frequently Asked Questions

Q: Muse told me there was no GitHub connector, but Meta announced GitHub support at Connect. What happened?

A: Both things were true at once. GitHub is one of the work connectors Meta explicitly supports, but the agent's directory lookup missed it in at least one reported case (reviewer Taylor Arndt's, after Connect). The agent then connected GitHub through the custom-connector path instead. "Doesn't exist" described the directory lookup, not the actual support.

Q: Does Meta review connectors before I connect them?

A: Only directory connectors. Submit at muse.ai/platform and Meta runs functional, security, and legal review plus end-to-end testing before listing. Custom connectors are not reviewed; Meta's consent dialog states this explicitly and tells you to check the provider's privacy policy.

Q: What scopes does a custom connector ask for?

A: It varies by service, but documented examples request openid, profile, email, and offline_access, meaning the connector keeps working when you are not actively using Muse. Scope it to what the task needs and disconnect what you don't use.

Q: Do custom connectors cost extra?

A: No separate fee. Custom connector usage draws from the same usage meter as everything else in the app, so a connector that polls a service constantly costs you the same tokens as a long conversation would.

Q: Can any service get into the directory?

A: Any service can submit at muse.ai/platform. Meta received more than 1,500 applications in under a week after the September 18 launch, and no review timeline has been published, so the queue is the bottleneck, not the bar.
